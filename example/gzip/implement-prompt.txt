What the specification leaves to you, and what the levels are for. The specification of `compress` is only the gzip header bytes and the round trip: `decompress(out) == Some(data)` for a member you choose. Everything about the encoder is yours — the parse, the block boundaries, the block types (stored, fixed, dynamic), the Huffman codes, the header's run-length coding — and so is what the levels mean. The intent, which you must take literally: RADICALLY OPTIMIZE LEVEL 1 FOR SPEED and RADICALLY OPTIMIZE LEVEL 10 FOR COMPRESSION RATIO. Level 1 should run at tens of MB/s like zlib or libdeflate at their level 1 (the cheapest match search that still finds copies, fixed Huffman codes or a cheap heuristic code, no exact code-length optimisation, nothing quadratic); level 10 should produce the smallest output you can reach with any amount of search and code fitting (optimal parsing, best length-limited codes, careful block splitting). The levels between trade one for the other, and both ends matter more than the middle. For the proof, a sound structure is to define your own encoder relation in Lean (what bits your code writes for a given plan), prove your code matches it, and prove once that whatever that relation writes decompresses to the input; keep that last lemma reusable so later changes to the code only re-prove the match.
